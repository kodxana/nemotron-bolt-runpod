# Runpod base compatibility — 2026-10-23

The image derives from `runpod/worker-v1-vllm:v2.30.0`, pinned to Linux/amd64 manifest `sha256:437ddeda2917d21fdd16c606d472db47129d0ab3ff55041db1801cbd81de475c`. Public registry metadata identifies CUDA 13.0.2, Python 3.12, vLLM release commit `5df63a7203cdb9328d824a27b682e77c7b9928be` and 9,465,244,778 bytes of compressed layers. The image itself was not pulled or executed on the authoring host.

The [official Dockerfile](https://github.com/runpod-workers/worker-vllm/blob/v2.30.0/Dockerfile) uses vLLM 0.32.0 and supports a baked-model workflow. Its release branch includes backported ModelOpt IQ2/Q8 support, but it is not the exact nightly prescribed by the [pinned NVIDIA model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB/blob/cf2effc5c4b794ee9fb8d34eab3d1d65ce64142f/README.md). The two refs have diverged; a simple version-number comparison is insufficient. Direct source comparison also found a DFlash padding-buffer change in NVIDIA's nightly.

This project therefore keeps the Runpod base and installs the exact NVIDIA nightly wheel, `0.32.0rc1.dev100+g77154ca61`, from the commit-specific upstream wheel URL. Its 326,952,120 bytes were streamed through SHA-256 locally, producing `92e3958a32e65f19ce19dea3cc7a2e1c9edd57565f461617841abfc0a66bcd98`. This confirms the pinned artifact identity; it does not verify GPU compatibility.

`inference-overlay.lock` also pins B12X 1.5.1, FastAPI 0.136.0, tokenspeed-mla 2.0.2, humming-kernels 0.1.16 and tokenspeed-triton 3.9.10.post20261008. The latter dependencies follow the actual nightly wheel metadata. CUDA, PyTorch, CUTLASS and FlashInfer are inherited. Installation uses `--no-deps --require-hashes`; recursive build checks fail if inherited package versions do not satisfy the resulting engine and B12X dependency trees. Build failure requires investigation rather than silently upgrading the stack.

The base installs the Runpod SDK in the inference environment, but SDK 1.12.0 requires a newer FastAPI than this vLLM engine permits. This project removes that global SDK and the unused optional bitsandbytes plugin, then installs the locked queue environment in `/opt/queue`. The entrypoint executes the original `/src/main.py` using `/opt/queue/bin/python`. All upstream startup, argument-builder, cache/preflight/error helpers and handler files remain unchanged. The startup invokes the global `vllm` executable because `PATH` is not switched to the SDK environment. `/local_model_args.json`, native environment variables and `VLLM_EXTRA_ARGS` supply the complete model recipe. No custom runtime package remains. Startup now has the original health gate, retries and error behavior.

The worker passes `/runpod-volume/models/bolt` directly to `vllm serve` and `/runpod-volume/models/lilicorr` directly in the speculative configuration. `MODEL_NAME` and `TOKENIZER_NAME` identify the local Bolt folder. There is no cache discovery. Both model folders and their revision markers are baked into the image, outside writable compilation caches. Deploy with no network volume attached and leave Model Store empty.

Sources inspected: [Runpod wrapper requirements](https://github.com/runpod-workers/worker-vllm/blob/v2.30.0/builder/requirements.txt), [vLLM release dependencies](https://github.com/vllm-project/vllm/blob/v0.32.0/requirements/common.txt), [nightly CUDA dependencies](https://github.com/vllm-project/vllm/blob/77154ca6116ae34cbfe314beef1016bde9b63989/requirements/cuda.txt), [nightly wheel index](https://wheels.vllm.ai/77154ca6116ae34cbfe314beef1016bde9b63989/vllm/).

The first Runpod build supplied on 2026-10-23 confirmed the overlay installation and Linux queue dependency check, then failed on mixed inherited OpenTelemetry versions: the gRPC exporter required shared components at 1.40.0 but found 1.45.1. The corrected overlay explicitly pins the API, SDK, protocol, umbrella exporter, gRPC/HTTP exporters and shared components to 1.45.1, plus their associated 0.66b1 packages. Version requirements and wheel hashes were checked against official PyPI metadata. The exact mismatch was reproduced with real installed packages and resolved by the same hash-locked package set; see [regression evidence](otel-regression.txt). Build checks remain strict and now report all dependency conflicts in one traversal.

A subsequent supplied runtime log shows the pinned engine loading the baked models at `max_model_len=32768`, completing readiness and finishing a queue job on an RTX PRO 6000 Blackwell MIG 48 GB instance. This supports admitting that exact 48GB partition alongside the full 96GB variants. The current eager-mode image still needs a rebuild and GPU comparison; final image identity and full feature acceptance remain release gates. Experimental 32GB presets require separate qualification. See [validation](VALIDATION.md).

The original startup and handler are MIT-licensed. Build checks verify the seven imported upstream files against their SHA-256 values in `scripts/build_checks.py`. Tests run that exact source: the actual argument builder processes Docker/Hub settings, the startup is checked with mocked engine processes, and the handler talks to a local HTTP fixture. The current original-startup/eager image still requires a rebuild and live GPU/Runpod gateway testing.
